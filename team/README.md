# ttScore Team v0.8.7

## Статус

- Версия: `v0.8.7`.
- Статус: `IMPLEMENTED LOCALLY, NOT PUBLISHED, NOT YET ACCEPTED`.
- Основа: принятая `v0.8.5`; структура публикации и спортивная логика сохранены; Live-отчёт и Live-табло текущей личной встречи теперь могут публиковаться для всех устройств через верхнеуровневые поля командного JSON.
- Назначение: создание, ручное обновление и публичное оглавление одной командной встречи.

`ttscore_team` не ведёт счёт личной встречи и не изменяет `ttScore 0.3.5`. Каждая личная встреча проводится отдельно в готовом `ttScore`. В `mode=edit` версия `v0.8.7` локально обнаруживает текущую встречу `ttScore 0.3.5`. Финальный результат автоматически сохраняется во временный локальный буфер. После запуска следующей личной встречи её Live-отчёт и Live-табло могут быть записаны в тот же JSON, который завершает предыдущую встречу и назначает новую `current`. После публикации JSON live-ссылки доступны в обычном публичном режиме и на других устройствах.

## Форматы

Каждый спортсмен команды A играет с каждым спортсменом команды B.

| Формат | Личных встреч | Побед для досрочного завершения | Возможная ничья |
|---|---:|---:|---:|
| 2×2 | 4 | 3 | 2:2 |
| 3×3 | 9 | 5 | Нет |
| 4×4 | 16 | 9 | 8:8 |

Для всех личных встреч командной встречи используется один выбранный формат: `Из 3 партий`, `Из 5 партий` или `Из 7 партий`.

## Создание командной встречи

```text
ttscore_team_0.8.7.html?mode=create
```

Форма принимает ID, дату, место, формат команд, формат личных встреч, названия команд и имена спортсменов. Расписание создаётся автоматически; до сохранения пары можно переставлять кнопками ↑ и ↓. Новый JSON содержит верхнеуровневые `liveReportUrl: null` и `liveScoreboardUrl: null`; они будут заполнены editor, когда для текущей личной встречи появится корректная live-публикация ttScore.

После проверки показываются расписание, путь `team/matches/<id>/<id>.json`, публичный URL и полный JSON. Файл сохраняется под точным именем `<id>.json`. Для публикации создаётся одноимённый каталог `team/matches/<id>/`.

Режим создания также загружает ранее скачанный подготовительный JSON `schemaVersion: 4`. Он восстанавливает форму и порядок пар. ID загруженной встречи остаётся заблокированным. Начатая встреча должна редактироваться в `mode=edit`.

## Публичный режим

```text
ttscore_team_0.8.7.html?match=<id>
```

Страница показывает сведения о встрече, составы, командный счёт, расписание и ссылки на постоянные отчёты завершённых личных встреч. `reportUrl` может вести, например, на автономный HTML-отчёт, открытый JSON или защищённый отчёт `ttScore`. Относительный `reportUrl` разрешается от каталога `team/matches/<id>/`, поэтому отчёты личных встреч можно публиковать рядом с `<id>.json`. Если в верхнем уровне JSON заполнены `liveReportUrl` и `liveScoreboardUrl`, у текущей личной встречи публично показываются кнопки `Live-отчёт` и `Live-табло`; локальный ttScore на устройстве зрителя не нужен.

Во время командной встречи статус показывает номер текущей личной встречи и порог побед. Окончание слова «встреча» согласуется с числом: `1 личную встречу`, `2–4 личные встречи`, `5+ личных встреч` с учётом исключений 11–14. `N` берётся из `order` текущей встречи, порог — из `winsToFinish`. После завершения командной встречи вместо этой строки показывается итог.

## Редактирование командной встречи

### Опубликованный источник

```text
ttscore_team_0.8.7.html?match=<id>&mode=edit
```

Редактор загружает опубликованный `team/matches/<id>/<id>.json`. Непосредственно перед подготовкой итогового JSON он повторно проверяет, что опубликованный источник не изменился.

### Локальный источник

```text
ttscore_team_0.8.7.html?mode=edit
```

Пользователь выбирает локально сохранённый `<id>.json`. Файл читается только браузером и никуда не отправляется. Опубликованный JSON в этом режиме не загружается и не сравнивается. Смешивать локальный и опубликованный источники в одной сессии нельзя.

В `v0.8.7` редактор расположен сразу после командного статуса, до полного публичного списка личных встреч. Это сокращает путь до основного действия в `mode=edit`, особенно для формата 4×4.

Для обоих источников редактор поддерживает:

- сворачиваемые рабочие разделы `Данные из ttScore`, `Изменения командной встречи`, `Отчёты личных встреч`, `Дата, место и составы`, `Запланированные личные встречи` и подготовленный preview; блок `Завершение текущей личной встречи` остаётся постоянно раскрытым;
- ввод, замену и допустимую очистку необязательного постоянного `Отчёта`;
- изменение даты, места, названий команд и имён спортсменов;
- перестановку только запланированных встреч кнопками ↑ и ↓;
- единое действие `Подготовить JSON с изменениями`, которое включает все текущие правки отчётов, сведений и planned-порядка;
- завершение текущей встречи, которое также включает весь текущий черновик редактора перед применением результата;
- операционные ссылки `Live-табло` и `Live-отчёт` у текущей встречи: в editor локальная ttScore live-публикация имеет приоритет, а при её отсутствии используются уже опубликованные верхнеуровневые ссылки из JSON;
- начальные значения `0:0` в `Итог по партиям`; стороны подписываются текущими названиями команд;
- отдельное `Перезагрузить источник` для опубликованного JSON непосредственно в рабочей области editor.

Для завершённой командной встречи `mode=edit` автоматически раскрывает общий раздел изменений и вложенный раздел отчётов; сведения, planned-порядок и блок перехода скрыты. `reportUrl` необязателен; опасные и некорректные URL отклоняются. Отсутствие `reportUrl` не блокирует переход личной встречи в `finished`. Legacy-поле `liveUrl` из файлов `v0.8.4` и более ранних принимается при чтении, игнорируется и удаляется при следующем сохранении JSON.

У завершённых и текущей встреч порядок фиксирован. При перестановке меняется только `order` запланированных встреч: стабильные ID личных встреч и их пары сохраняются.

Нажатие на запланированную встречу выделяет её цветом. После нажатия ↑ или ↓ выделяется перемещённая встреча уже на новой позиции. Одновременно выделяется только одна строка; выделение хранится только в интерфейсе по стабильному ID и не изменяет JSON. Текст встречи доступен как обычная кнопка, поэтому выделение работает также с клавиатуры Enter/Space.

В режиме редактирования нельзя менять:

- ID командной встречи;
- формат 2×2, 3×3 или 4×4;
- формат личных встреч;
- ID спортсменов;
- ID и состав пар личных встреч;
- результат уже завершённой встречи.

Перед заполнением формы проверяется канонический порядок ID спортсменов `a1…aN` и `b1…bN`. Это исключает запись исправленных имён не тем спортсменам.

Отмена последнего завершения личной встречи в `v0.8.7` не реализована.

## Локальная интеграция с ttScore 0.3.5

Интеграция работает только в `mode=edit` и только когда `ttScore` и `ttscore_team` доступны под одним origin. Целевое размещение — `https://t39s.github.io/ttscore/` и `https://t39s.github.io/ttscore/team/...`.

`ttscore_team` читает существующие данные `ttScore 0.3.5` без изменения самого `ttScore`:

- `localStorage["ttScore:0.3.5:currentMeeting"]`;
- `localStorage["ttScore:0.3.5:livePublication"]`;
- `BroadcastChannel("ttScore:0.3.5:meeting")` как сигнал перечитать данные;
- `storage` event как резервный сигнал между вкладками.

В редакторе появляется блок `Данные из ttScore`. Имена спортсменов сопоставляются после удаления крайних пробелов, схлопывания внутренних пробелов и без учёта регистра. Поддерживаются прямое и обратное расположение A/B; при неоднозначности или несовпадении перенос блокируется.

Live-доступ текущей личной встречи работает в двух контурах:

- в `mode=edit` `Live-табло` и `Live-отчёт` вычисляются из локальной `livePublication`; обе ссылки используют тот же `publisherUid` и ключ, различается только `page=scoreboard` / `page=report`;
- при любом следующем действии `Подготовить JSON с изменениями` локально обнаруженная пара ссылок автоматически записывается в верхнеуровневые `liveScoreboardUrl` и `liveReportUrl`; отдельного действия копирования или переноса live нет;
- если локальная live-публикация временно недоступна, уже опубликованные live-ссылки сохраняются при обычных правках текущей встречи;
- при `current → finished` обе верхнеуровневые live-ссылки очищаются до назначения следующей `current`;
- после ручной публикации `<id>.json` публичный режим показывает обе ссылки на любом устройстве.

По явному действию пользователя `Перенести результат` заполняет существующие `gamesA/gamesB`; JSON в этот момент не изменяется — дальнейшая подготовка выполняется штатными действиями редактора.

Финальный результат берётся из уже сформированных `ttScore` партий `games + pendingGame`; правила розыгрышей в `ttscore_team` не дублируются. `ttscore_team` не читает Firebase и не расшифровывает live-данные. `reportUrl` интеграция не создаёт.

Если данных `ttScore` нет, они несовместимы или браузер не даёт доступ к хранилищу, ручной workflow редактора остаётся полностью доступным. Polling не используется.

## Сохранение JSON на разных устройствах

В интерфейсе остаётся одна кнопка `Сохранить JSON`. Приложение само выбирает первый доступный механизм без определения модели устройства или браузера:

1. `showSaveFilePicker()` — диалог выбора имени и папки, если браузер его поддерживает.
2. `navigator.share({ files })` — системное меню, в котором на iPhone/iPad можно выбрать `Сохранить в Файлы`.
3. Blob-ссылка с атрибутом `download` — последний резервный вариант.

Все механизмы получают один и тот же объект `File`, точное имя `<id>.json` и точные байты подготовленного JSON. При отмене системного диалога следующий механизм не запускается. При технической ошибке приложение пробует следующий доступный механизм.

Папка заранее не настраивается: её выбирает пользователь в системном интерфейсе, если это допускает браузер и операционная система.

Для сохранения через Web Share вызов системного меню выполняется непосредственно внутри нажатия кнопки, без предварительного асинхронного запроса. Поэтому опубликованный источник проверяется перед созданием preview, а кнопка сохраняет именно проверенный и показанный JSON. Любое изменение формы или порядка встреч аннулирует preview и требует подготовить его заново. Источник теоретически может измениться уже после создания preview, поэтому проверка GitHub diff перед commit остаётся обязательной.

## Ручная публикация JSON и отчётов

1. Сохранить подготовленный `<id>.json`.
2. Открыть или создать в GitHub каталог `team/matches/<id>/`.
3. Загрузить в него `<id>.json`, заменив предыдущую редакцию при её наличии.
4. В этот же каталог загружать отчёты завершённых личных встреч. Для файлов рядом с JSON в `reportUrl` можно использовать относительную ссылку вида `./<report-file>`.
5. Проверить GitHub diff.
6. Создать commit.

Приложение не использует GitHub API, токены, авторизацию, Firebase или серверную часть.

## Модель JSON

Версия сохраняет `schemaVersion: 4`. Поле `individualMatchBestOf` принимает только `3`, `5` или `7`. На верхнем уровне JSON используются `liveReportUrl` и `liveScoreboardUrl`: они относятся только к текущей личной встрече, должны быть заданы парой либо равны `null`, а для завершённой командной встречи обязаны быть `null`.

Редактор принимает только `schemaVersion: 4` и точное имя `<id>.json`. Для незавершённой командной встречи требуется ровно одна текущая личная встреча. Завершённую встречу можно открыть только для изменения постоянных отчётов. JSON `v0.8.5` без верхнеуровневых live-полей продолжает читаться и получает их при следующем сохранении. Legacy-поле `liveUrl` внутри объектов личных встреч допускается только для чтения и удаляется при следующем сохранении.

Модель проверяет размеры команд, полное покрытие пар, порог побед, последовательность статусов, результаты личных встреч, дату, `updatedAt`, допустимые `reportUrl`, `liveReportUrl` и `liveScoreboardUrl`, парность верхнеуровневых live-ссылок, целые JSON-числа и отсутствие неизвестных полей. `reportUrl` остаётся допустимым, но необязательным и для `finished`. Новые JSON-файлы `liveUrl` внутри личных встреч не содержат.

## Пакетный цикл между личными встречами (v0.8.7)

После финала текущей ttScore-встречи Team сохраняет минимальный `pendingFinishedMatch` в локальном хранилище устройства судьи. Пока `matchId` не изменился, Undo автоматически отменяет этот временный финал. После запуска следующей ttScore-встречи сохранённый результат остаётся доступным; новая пара должна совпасть со следующей `planned`-встречей. Если для неё уже включён live, один подготовленный JSON одновременно завершает предыдущую встречу, назначает следующую `current` и записывает её `liveReportUrl`/`liveScoreboardUrl`. Если live ещё нет, тот же переход можно подготовить без live. После появления нового `matchId` судья может вручную скорректировать сохранённый результат: последующие события live/storage новой встречи не перезаписывают такую корректировку. После загрузки опубликованного JSON Team удаляет локальный буфер, если этот результат уже присутствует в нём как `finished`.
